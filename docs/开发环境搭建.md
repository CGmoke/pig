> 宿主 Ubuntu 24.04 + ROS 2 Jazzy ｜ 目标 Ubuntu 22.04 + ROS 2 Humble + Isaac Sim 4.5
> 制定日期：2026-11-19（距初赛提交 6 天）

---

## 0. 先回答一个容易被绕过的问题

「比赛要求 22.04 + Humble」——这条约束到底在约束什么？

它不是在约束你的**桌面系统**，而是在约束一个 **ABI 契约**：Isaac Sim 4.5 自带的 Python 是 3.10，ROS 2 Bridge 的 `libisaacsim.ros2.bridge.so` 是针对 Humble 的 `rclpy` / `rmw` 在 22.04 上编译出来的。这意味着——

> **跑 Isaac Sim 的那个进程，必须能 `import rclpy` 到 Humble。** 其余一切都是这条的推论。

由此可以直接推出三件事：

1. 宿主 24.04 完全不用动。它只负责：显卡驱动、Docker、显示、写代码。
2. 你已经在 docker 里装好的那个 `ubuntu:22.04 + humble` **不能用来跑 Isaac Sim**（没有 Isaac Sim，也没有 Omniverse 运行时），但它可以当"算法/工具容器"或干脆弃用。
3. 真正要新建的，是一个 **以 Isaac Sim 官方镜像为底座、内部再装 Humble** 的镜像。这样 Python 3.10、Omniverse、Humble 三者天然对齐，不用你手工调 ABI。

那为什么不反过来——在 22.04 里自己装 Isaac Sim？因为 4.5 只官方支持 22.04 的**裸机安装**，容器化路径官方只维护 NGC 镜像；自己装 Omniverse Launcher 在无 GUI 容器里是纯自找麻烦。**站在官方镜像上做加法，是这几天唯一省时间的路线。**

## 0.6 本网络的三个硬约束（实测，不是猜的）

这三条直接决定了 Dockerfile 为什么长这样，换台机器可能需要回退：

| 现象 | 实测证据 | 处置 |
|---|---|---|
| 容器内 HTTPS 不可用 | `https://packages.ros.org` → `certificate verify failed`；`https://raw.githubusercontent.com` → 连接被重置；而 `http://packages.ros.org` 返回 200 | 所有源改走 **http**；不要用 `curl https://raw.githubusercontent.com/...ros.key` 这类写法 |
| ROS 官方 key 已过期 | `apt-get update` 报 `EXPKEYSIG F42ED6FBAB17C654`；`ros.key`(1167B) 与 `ros.asc`(1678B，去封装后同尺寸) 是同一把 AB17C654 | 用 `[trusted=yes]` 跳过签名校验 |
| nvcr.io 不在镜像站覆盖范围 | `daemon.json` 里 3 个 mirror 都是 Docker Hub 的；nvcr.io 只能直连 | 直连拉取即可（manifest 已验证可达），慢就挂后台 |

> **这是妥协，不是最佳实践。** `trusted=yes` 意味着放弃 apt 的包签名校验。在能走 HTTPS 的网络里，请把 `docker/Dockerfile.sim` 里那行 deb 换回 `[signed-by=...]` 的写法——注释里留了原文，改回去只改一行。

## 2. 三道硬闸门（按顺序，不通过不往下走）

### 闸门 1：GPU 穿透进容器

```bash
# 1) 装 toolkit
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
  | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit

# 2) 注册到 docker 并重启
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# 3) 验收：容器内必须能打印出 GPU 表
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi
```

**验收标准**：上一条命令输出里能看到 `NVIDIA GeForce RTX 4060 ... 8GB`。
看不到就不要 pull Isaac Sim——14 GB 白下载，然后你会以为是镜像问题，浪费半天。

### 闸门 2：磁盘

Isaac Sim 4.5 镜像约 14 GB 压缩、解压后 30 GB+；再加 Humble（~2 GB）、构建缓存、资源包、录屏素材，**至少留 70–80 GB**。

```bash
du -sh ~/.cache/* 2>/dev/null | sort -h | tail -10   # 38G 在这里
docker system df
```

两条路，选一条：

- **清**：`~/.cache` 里多半是 pip / 浏览器 / 构建残留，能腾 20–30 GB。
- **迁**：把 docker data-root 挪到大盘（若你有第二块 NVMe）：
  ```bash
  sudo systemctl stop docker
  sudo mkdir -p /data/docker && sudo rsync -aHAX /var/lib/docker/ /data/docker/
  echo '{"data-root": "/data/docker"}' | sudo tee /etc/docker/daemon.json
  sudo systemctl start docker
  ```

### 闸门 3：显示（可以绕开，但要提前决定）

主机是 Wayland 时，容器里跑 Isaac Sim GUI 经常卡在 GL 初始化。两条路：

| 方式 | 命令 | 代价 |
|---|---|---|
| **WebRTC livestream（推荐）** | `isaac-sim.streaming.sh`，浏览器开 `https://<ip>:8211/streaming/webrtc-client` | 无 X 依赖，8 G 显存也更省；延迟 ~50 ms 可接受 |
| X11 直出 | `xhost +si:localuser:root` + 挂 `/tmp/.X11-unix` | 偶发花屏、缩放错乱 |

6 天冲刺期不要在这上面纠结，**直接选 livestream**。

## 3. 容器边界怎么画：单容器 vs 双容器

这是本方案唯一需要你做判断的地方，想清楚再动手。

| | 单容器（Isaac Sim + Humble + 你的节点） | 双容器（sim 容器 + 算法容器，host 网络互通） |
|---|---|---|
| DDS 坑 | 无（同进程组、同 shm） | 有：FastDDS 跨容器共享内存经常"能 list 收不到数据" |
| 桥接构建 | 桥就在本容器，`source` 即可 | 桥仍在 sim 容器，算法容器只需 humble（ABI 一致就行） |
| 并行开发 | 弱（一个环境，改坏了要重建） | 强（队友可以只跑算法容器） |
| 镜像体积 | ~35 GB | 35 + 3 GB |
| 调试心智负担 | 低 | 中（多一层网络/时序） |

**我的建议：单容器打天下，双容器留作后期优化。** 理由很实在——你只有 6 天，而"两端话题对不上"这种问题，排查一次就要耗掉半天。等 T1/T2/T3 都跑通了、队友要并行改算法了，再拆第二个容器，那时你已经知道 DDS 该怎么配。

判断依据其实很简单：**你有没有一个"必须独立部署"的模块？** 现在没有。所以别拆。

## 4. 落地步骤（每步都有验收点）

### Step 1 · 建镜像

```bash
cd /home/moke/WorkBuddy/Eight-Realms
docker compose -f docker/compose.yaml build     # 首次拉 isaac-sim:4.5.0，慢，可后台跑
```

> **本机已完成这一步**：`bajie/sim:humble45`（23.7 GB）已在本地，无需重建。
> 实测拉取耗时约 1 小时（nvcr.io 约 1 MB/s），构建再 4.5 分钟。换机器时才需要重来。

`docker/Dockerfile.sim` 做的事：官方镜像 → 清空 ENTRYPOINT → 装 `ros-humble-ros-base` + `xacro` + `colcon` + `rmw-cyclonedds-cpp` → 写好 `.bashrc` 自动 source。

**验收**：
```bash
docker compose -f docker/compose.yaml run --rm sim bash -lc \
  "ros2 --version && xacro --version && ls /isaac-sim/isaac-sim.sh"
```

### Step 2 · 确认 ROS 2 Bridge 就位（已实测）

```bash
# 注意：主库在 bin/ 下，不在 humble/lib/ 下——后者是它自带的一整套 ROS 运行库
docker run --rm bajie/sim:humble45 bash -lc '
  export LD_LIBRARY_PATH=/isaac-sim/exts/isaacsim.ros2.bridge/humble/lib:$LD_LIBRARY_PATH
  ls -l /isaac-sim/exts/isaacsim.ros2.bridge/bin/libisaacsim.ros2.bridge.humble.so
  /isaac-sim/exts/isaacsim.ros2.bridge/bin/isaacsim.ros2.bridge.check; echo "check exit=$?"'
```

自检返回 `exit=0` 且无输出 = 库能正常加载、无缺失符号。

这一点值得记牢：**Isaac Sim 镜像自带一套 Humble 运行库**（`humble/lib` 下有 `librcl*`、`librosidl*`、`librclpy` 等）。我们额外 apt 装的 `ros-humble-ros-base` 提供的是**工具链与你自己节点的编译环境**（`ros2` CLI、`colcon`、`xacro`）。两者版本必须同代（都是 Humble / py3.10），否则会出现"能加载但消息序列化对不上"的诡异问题。

**验收**：场景加载后 `ros2 topic list` 能看到 `/clock`、`/joint_states`。

### Step 3 · 复现官方场景

```bash
bash scripts/run_sim.sh livestream        # 浏览器打开 8211 端口
# 或纯无头体检：
docker compose -f docker/compose.yaml run --rm sim \
  /isaac-sim/python.sh /workspace/scripts/smoke_sim.py
```

`scripts/smoke_sim.py` 会打印三件事，**先看清再动手写代码**：

1. `Articulation Root` 有几个、在哪（没有就得手工加 API）
2. 每个关节的 `localPos0`（这就是 origin，是你后续比对的基准）
3. **场景里已经有哪些 `ROS2*` 节点** ← 最关键

第 3 条决定了你要不要自己搭 ActionGraph。如果官方场景已内置 `ROS2PublishJointState` / `ROS2PublishClock` / `ROS2PublishTransformTree`，你再搭一遍的后果是：**双发 `/clock`（时间戳跳变、物理步进抖动）、双发 `/tf`（TF 树报 duplicate）**，而报错信息完全不会告诉你"是你多搭了一个"。

**怎么区分"没接 GPU"和"配置写错了"**：我在这台机器上无 GPU 实测过，特征很明确——

```
[extensions 全部加载成功，含 isaacsim.asset.importer.urdf-2.3.10]
...
Segmentation fault (core dumped)
```

即 **kit 起来、扩展加载完、最后在 RTX 初始化处段错误**。看到这个就当 GPU 问题处理（`docker run --gpus all` 是否生效），不要去翻 Python 代码。反过来，如果日志停在 `omni.ext` 之前就挂了，那才是镜像或环境的问题。

### Step 4 · 展开 URDF 并导入

```bash
# 展开（容器内）
bash scripts/expand_urdf.sh
```

导入有两个入口，**先用 GUI 手工走一遍**，看清每个勾选项，再把参数固化到脚本：

- GUI：`File > Import`（4.5 里 URDF 导入已并入统一导入对话框；老版本在 `Isaac Utils > Workflows > URDF Importer`）
- 脚本：`isaacsim.asset.importer.urdf._urdf`，`ImportConfig()` 逐个字段设置

勾选项的判据（**这是"保留官方模型"的成败线**）：

| 选项 | 设成 | 为什么 |
|---|---|---|
| `Merge Fixed Joints` | **关** | 开了会把 fixed 连杆合并掉，`check_urdf_origin.py` 立刻报"关节缺失" |
| `Collision From Visuals` | 关 | 保留原 URDF 的 collision，而不是拿 visual 顶替 |
| `Fix Base Link` | **看 T1 要求** | T1 是"动起来"，若含底盘平移就必须**关**，否则底盘焊死在原地 |
| `Joint Drive Type` | Position | 机械臂关节用位置驱动；continuous 关节记得配 stiffness/damping |
| `Self Collision` | 关 | 省算力，8 G 显存下尤其重要 |
| `Convex Decomposition` | 按需 | 默认 convex hull 够用；要精确接触再开，代价是导入变慢 |

**验收**：
```bash
docker compose -f docker/compose.yaml run --rm sim \
  /isaac-sim/python.sh /workspace/scripts/check_urdf_origin.py \
  /workspace/generated/bajie_robot.urdf /workspace/generated/bajie_robot.usd
```
必须打印 `✅ 连杆与关节 origin 与官方 URDF 完全一致`。这行输出**直接放进提交材料**——它是"基于官方模型"最硬的证据。

### Step 5 · 接桥、跑通 T1

ActionGraph 最小集合（缺一不可）：

```
OnPlaybackTick ──┬─→ ROS2PublishClock            → /clock        （否则所有节点都收不到仿真时间）
                 ├─→ ROS2PublishJointState       → /joint_states  （robot_state_publisher 的输入）
                 ├─→ ROS2PublishTransformTree    → /tf /tf_static
                 └─→ ROS2PublishOdometry         → /odom          （底盘有轮子时）
ROS2SubscribeJointState → ArticulationController   ← /joint_command （你的控制指令入口）
ROS2CameraHelper ×N     → /camera/*/image_raw     （T2/T3 的输入）
```

时序上有个坑：`ROS2Context` 节点必须接在 `OnPlaybackTick` 之前、且 `domain_id` 与容器 `ROS_DOMAIN_ID` 一致，否则你在容器里 `ros2 topic list` 永远是空的——而这个空不会报错。

## 5. 坑清单（每条都是半天起步的）

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | `ros2 topic list` 空 | ROS2Context 没接 OnPlaybackTick / domain_id 不一致 | 见 Step 5 |
| 2 | 话题能 list，`hz` 一直在等 | FastDDS 跨容器 SHM 段不通 | `--ipc=host` + `--shm-size=2g` |
| 3 | TF 树报 duplicate | 场景已有 PublishTransformTree，你又加了一个 | 删自己加的 |
| 4 | 夹爪不动 | URDF 里有 `mimic` joint，Isaac 不支持 | 用 controller 做联动，别指望导入 |
| 5 | 底盘原地打滑 | `Fix Base Link` 勾了 / 轮子摩擦参数为 0 | 取消勾选；调 `physics:material` 摩擦 |
| 6 | 启动即 OOM | 8 G 显存 + 默认分辨率 + 光追 | `--no-window` + livestream 降分辨率；关 path tracing |
| 7 | 导入后模型巨大或倒挂 | URDF 单位/坐标约定与场景不一致 | 场景是米制 Z-up；用 `check_urdf_origin.py` 定位是哪一节偏移 |
| 8 | 重建镜像后容器里 30 GB 垃圾 | 没清 build cache | `docker builder prune` |
| 9 | **启动即段错误，崩在 `librtx.scenedb.plugin.so`**（Vulkan 正常枚举到 GPU 之后） | 驱动 595.x 未被 Isaac Sim 验证，RTX 渲染器初始化崩溃。与 NVIDIA 官方论坛确认的案例同签名（595.x + librtx.scenedb） | **降级驱动到验证版本**（4.5 用 550 系列，见第 8 节）；`VK_ICD_FILENAMES`、`activeGpu`、关 DLSS 均无效，已实测 |
| 10 | 启动立刻退出，日志只有一句 `Omniverse Kit cannot be run as the root user` | 镜像 `USER root`，但镜像环境和 `run_sim.sh` 都没带放行开关 | 加 `-e OMNI_KIT_ALLOW_ROOT=1`（或 `--allow-root`）。已写进 `run_sim.sh` |
| 11 | 跑了 16 秒后 `XIO: fatal IO error 0 (Success) on X server ":1"`，退出码 1 | GDM 会话下 `~/.Xauthority` 不存在，`docker -v` 对缺失源路径会**自动建一个空目录**挂进去，容器内 `/root/.Xauthority` 成了目录，X 认证失效 | 挂真实 cookie：`/run/user/$(id -u)/gdm/Xauthority`。`run_sim.sh` 已改为自动探测（找不到就退回 xhost）。**注意先 `rmdir ~/.Xauthority` 清掉那个假目录** |
| 12 | 窗口开了但里面是空的，显存只有 1.8 G，日志只有 `World0.usd` | 把 usd 路径当位置参数传给 `isaac-sim.sh` **不会触发 open_stage**，Kit 停在默认空场景 | 用 `scripts/run_gui.py`：`SimulationApp(headless=False)` + `open_stage()` + `timeline.play()` |
| 13 | `librmw_fastrtps_cpp.so: cannot open shared object file`，`ROS2 Bridge startup failed` | GUI 直接起 `isaac-sim.sh` 没 source Humble，`LD_LIBRARY_PATH` 为空（库其实在 `/opt/ros/humble/lib`） | 启动前 `source /opt/ros/humble/setup.bash`；`run_sim.sh` 已统一加 |
| 14 | 场景打开了但不下发任何 ROS 话题 | 官方桥接图是独立 USD（`omni_graphs/*.usd`），`abr_scene.usd` 里没有 | 见 README「当前卡点」：需 `mount_graphs.py` 挂图 |

## 8. 当前唯一阻塞：驱动版本与 Isaac Sim 4.5 不兼容（2026-11-20 实测定性）

> **状态更新（2026-11-20 12:20）：已解除。** 本机现为驱动 `580.178.04`，RTX 4060 上
> 完整跑通了 GUI：`app ready` → RTX PSO 编译 → 场景载入，全程无 `librtx.scenedb` 段错误。
> 结论仍成立：595.x 不可用，降到 550/580 这条线即可。下面各条保留作为崩溃签名参考——
> 将来若再出现「起不来」，先看崩溃点是否还是 `librtx.scenedb.plugin.so`。

### 证据链（四个实验，缺一不可）

1. 官方入口 `runheadless.sh` 与 Python API 两种方式**都崩**，排除我们用法问题；
2. Vulkan 在容器内正常枚举出 RTX 4060（`vulkaninfo` 确认），崩溃发生在枚举成功之后；
3. 强制 NVIDIA ICD（`VK_ICD_FILENAMES`）+ `--/renderer/activeGpu=0` + 关 multiGpu/DLSS，**崩溃不变**；
4. 崩溃点固定在 `librtx.scenedb.plugin.so`（RTX 渲染器建场景库阶段）。NVIDIA 官方论坛存在同签名案例：驱动 595.x + Isaac Sim 崩在同一库，官方答复「595.x 未经验证，请降到验证版本」。

结论：**驱动 595.99.02 与 Isaac Sim 4.5 的 RTX 渲染器不兼容**。这不是配置错误，没有任何参数能绕过去。

### 修复：驱动降级到验证版本（需要你执行，涉及重启）

```bash
# 1. 看仓库里有哪些可用版本
apt list 2>/dev/null | grep -E "^nvidia-driver-(550|535)"

# 2. 装 550 系列（保持 open 内核模块，与当前一致；RTX 4060/Ada 完全支持）
sudo apt install -y nvidia-driver-550-open

# 3. 重启并确认
sudo reboot
nvidia-smi        # 应显示 550.x

# 4. 回归验证（应全绿，且不再段错误）
sudo bash scripts/setup_host.sh
```

若 550 仍崩，退到 535：`sudo apt install -y nvidia-driver-535-open`。
